1.46 ×, 1.53 ×): the realised `EdgeSet` (≈ 298 MB at order 2500) stayed on the device

**Order 200 diagnosis** (GPU 1, f32, MiB, `peak_bytes_in_use` after the first
1000 ms window; diagnostic `mem_diag3.py`, not a gate run):

| XLA setting | old `Simulator` | kernel, auto storage (Dense recurrent) | kernel, CSR forced |
|---|---|---|---|
| default (`xla_gpu_redzone_padding_bytes` = 8 MiB) | 49.1 | 70.3 | 65.1 |
| redzone 1 MiB | 7.1 | 15.5 | 9.1 |
| redzone 64 KiB, 0, or `xla_gpu_autotune_level=0` | 5.4–5.5 | 14.6 | 5.1 |

The order-200 peak is XLA's autotuning scratch: every buffer of an autotuned fusion is
padded with 8 MiB redzones on each side during the first compile. Both
implementations pay it; the kernel has about one more buffer pair (≈ 16 MiB). Without
it, the kernel with CSR storage matches the old `Simulator` (5.1 vs 5.4 MiB), and the
Dense choice of `make_storage('auto')` at order 200 costs ≈ 9 MiB more (the 4 MB matrix,
the 1 MB mask and where/matmul temporaries). CSR is also faster at order 200 (f32
0.0601 vs 0.0686 ms/step, f64 0.0924 vs 0.1064). Rollout temporaries are small (same
peak for 100 ms and 1000 ms windows). In this diagnostic, the order-2500 peak was
144.7 MiB at every redzone setting. Under the full G3 protocol, however, the kernel's
order-2500 f32 peak fell from 197.6 MiB (after K1a-8) to 144.6 MiB (after K1a-9), so the
redzone also matters there under the warm-up-until-no-compilation protocol. Step time
does not change with the redzone size.

**Resolution (K1a-9, orchestrator decision, option C).**

- (A) Every kernel jit gets the per-jit compiler option
  `xla_gpu_redzone_padding_bytes = 64 KiB` (`_kernel/xla.py`). Users' jits and
  `XLA_FLAGS` are untouched (tested). The trade-off: a faulty autotuning candidate that
  writes more than 64 KiB out of bounds is no longer caught.
- (B) `make_storage('auto')` picks CSR on GPU. Across the sweep, CSR/Dense step is
  ≤ 1.06 and CSR memory is always lower (`2026-10-23-K1a-9-storage.json`). The CPU is
  unchanged.

With both, the kernel's order-200 peak falls from 70.3 to 6.2 MiB (f32). The metric
and criterion are unchanged: raw peak vs the T0 row, ≤ 1.1 ×.

### 3.7 Correctness note: brainevent#204 (float64 binary events on GPU)

On GPU, brainevent 0.2.1 computes `BinaryArray(x float64) @ dense W` wrongly and raises
no error (filed as brainevent#204 during K1a-7). The kernel's binary payload path
passed float64 spikes in float64 runs. Every float64 GPU run that used **Dense**
storage was therefore wrong. Since K1a-10 (PR #121), the kernel casts these events to
float32, which is exact for 0/1 values. The fix is verified on GPU 1: Brunel float64
Dense and CSR agree at orders 200 and 800.

Results affected:

- **K1a-7 G3, float64 order 200, measured before K1a-10** (the post-K1a-8 history table
  in §3.3). It used Dense and fired at 59.7 Hz against 57.2 Hz for the old
  `Simulator`. Superseded by the final G3 table, measured after K1a-10.
- **K1a-4 `gpu64cs_brunel400`, scalar-delay rows** (`2026-10-22-K1a-4-delays.json`).
  `auto` chose Dense; they fired at 57.68 Hz on GPU against 52.44 Hz on CPU. Their
  rate column is wrong. Their step times are kept, because the cost of the binary
  Dense kernel does not depend on the event values. The results README carries the
  correction.
- **K1a-9 storage sweep**: its GPU float64 Dense rows were re-measured after K1a-10.

Results unaffected:

- float32 runs;
- CPU runs (K0 G9 / T10, the G1 compile times, G5 and the G4 CPU rows);
- the old `Simulator` (T0);
- CSR rows, including the `cusparse` float64 rows at order 2500 and the K1a-4 order-2500
  rows, whose rates equal the CPU rows;
- the per-edge-delay scatter rows;
- G2: its spec network uses CSR and is silent.

## 4. Decisions

All decisions are in spec §7 (rows K1a-1 … K1a-8). Lead decisions taken during K1a-7:

- AI point for G5: order 2500, `g = 16`, `η = 4`, 10 seeds each side.
- G3 memory: fix it now and keep the metric (raw peak device memory, ≤ 1.1 × T0) →

- `iaf_psc_exp` promoted to the model library with model tests and NEST parity.
- G1, G4 and G5 kept as measured before K1a-8.

Decisions delegated by the lead to the orchestrator (2026-10-23):

- **K1a-9 (option C, PR #122)**, to fix the order-200 G3 memory failure without
  changing the metric:
  - (A) a per-jit `xla_gpu_redzone_padding_bytes = 64 KiB` on every kernel jit. It is
    never global; user jits and `XLA_FLAGS` keep XLA's default.
  - (B) `make_storage('auto')` picks CSR on GPU, from the measured crossover. The CPU
    is unchanged.
- **K1a-10 (PR #121)**: binary-path float64 events are cast to float32 before
  brainevent (brainevent#204). For Dense, a `custom_jvp` keeps the event gradient in
  float64. bool was rejected because it zeroes the event gradient.
